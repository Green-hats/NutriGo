# NutriGo 产品方案

更新日期：2026-09-20。本文描述当前产品方向与功能边界；Android 1.0.0、生产服务及客户端兼容状态见[路线图](ROADMAP.md)，技术设计见[架构文档](ARCHITECTURE.md)。

## 产品定位

NutriGo 是用于日常饮食记录与营养参考的手机 App。用户可以拍照生成食物和份量草稿、修正后记录一餐，再结合饮食历史与健康档案进行 AI 对话。图片估重、营养数据库与模型回复都属于参考，不把它们包装成称量结果或临床判断。

| 目标人群 | 主要需求 | 对应入口 |
|---|---|---|
| 日常饮食管理用户 | 减少手工录入、回顾每天吃了什么 | 拍照、手动记录、按日期日记 |
| 体重和健身管理用户 | 观察热量与宏量营养素变化 | 每日合计、7 / 14 / 30 天趋势 |
| 希望了解营养知识的用户 | 根据自己的记录提出问题 | AI 对话、档案与教材检索工具 |

健康档案可记录过敏原、基础病及目标，供回答参考；应用不提供疾病诊断或治疗功能。

## 核心体验

1. 注册登录，在“我的”填写健康档案。
2. 在日记选择日期，通过拍照、相册或手动录入记录这一餐。餐次按当前手机时间默认选中，允许自行修改。
3. 照片生成多项食物、克重范围和营养草稿；用户调整食用量后确认，整餐事务保存，重复提交防重。
4. 查看历史日记与实时汇总，在对话中查询记录、档案、趋势和营养知识；工具详情可展开核对。

界面保留对话、日记、我的三个入口，减少重复解释及操作按钮。估重假设等细节放入展开区域；断网、加载失败、数据为空和凭证失效分别呈现。

## 系统与数据边界

客户端采用 Tauri 2 / Rust、React / TypeScript / MUI；云端使用 Go 数据服务和 Python Agent，由 Caddy 暴露单个 HTTPS 入口。页面随安装包分发，云端不需要托管前端网页。

账号、健康档案、饮食和会话保存在云端 SQLite，照片保存在云端卷。照片分析会将图片提交至 DeepSeek；聊天会向配置的 LLM 发送对话以及相关工具上下文。本地 BGE 与 ChromaDB 执行教材检索。服务端 Key 不写进安装包，但手机登录令牌当前仍在 WebView localStorage，原生安全存储尚待完善。

产品是在线应用，没有离线同步或离线 AI；只读 preview 包仅用于界面体验。聊天供应商通过 LiteLLM 配置，新版照片分析当前固定使用 DeepSeek 官方端点，并非所有模型均可直接替换。

## 验收原则

| 场景 | 验收目标 |
|---|---|
| 一餐记录 | 可调整菜名、克重、营养和餐次；全部保存或全部失败；不因重试多记一餐 |
| 历史与日期 | 不丢弃旧明细；补记、编辑和删除反映到对应日期；AI 使用配置的业务日期 |
| AI 数据引用 | 数据来自本人认证身份；工具失败必须如实反馈；可核对返回详情 |
| 照片 / 教材能力 | 通过代表性图片和问题集评估；不以能启动替代效果验收 |
| 手机使用 | 真机验证系统栏、键盘、拍照、权限、网络断开与恢复 |
| 数据恢复 | 备份有完整性验证并能在隔离目录恢复；异地能力以真实存储读回验证为准 |

尚未建立可支撑“3 秒识别”“准确率超过 80%”或固定营养误差的评测集，因此不把这些数值列为已达成指标。具体剩余任务及验收标准列在[路线图](ROADMAP.md)。
